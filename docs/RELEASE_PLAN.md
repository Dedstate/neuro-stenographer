# План одного разработчика: от блокеров к полировке

## P0 - получить проверяемый APK

- [x] Единый Android Gradle-проект вместо разрозненных Kotlin-файлов.
- [x] Один Sherpa API/JNI 2.0.1 для ASR и диаризации.
- [x] Встроенные веса, SHA-256, отсутствие разрешения INTERNET.
- [x] Импорт, PCM mono 16 kHz, диаризация, ограниченные ASR-фрагменты, таймкоды, экран, JSON.
- [x] Специализированная RUPunct вместо генеративного runtime/Qwen.
- [ ] Чистая установка APK на целевое устройство/эмулятор 4 ГБ, авиарежим **до первого запуска**.
- [ ] Три незнакомые записи подряд: нет аварий, JSON проходит `scripts/evaluate.py`.

Последние два пункта - стоп-факторы для объявления решения готовым. Рабочие команды приведены ниже. Не тратить это время на смену ASR или красивый экран.

## P1 - качество, где находятся основные баллы

1. Разметить 3-5 русских диалогов: разные голоса, короткие ответы, шум, перебивания. Разделить набор на настройку и независимую проверку.
2. Измерить WER исходного ASR, ошибки спикеров и границ. Пунктуация не должна ухудшать лексический WER.
3. Перепроверить ERes2Net: имеющийся командный baseline ошибается. Сравнить пороги кластеризации на наборе настройки, затем проверить выбранный порог на отложенных записях. Не фиксировать «2 спикера» и не выбирать порог по одной демонстрационной записи.
4. Если эмбеддинги не различают русские голоса достаточно хорошо, сравнить альтернативную speaker-verification модель с русскими/многоязычными данными. Выбирать по измерению ошибок, а не только названию или языку training dataset.
5. Обработку наложений сейчас считать ограничением. Независимый ASR одного смешанного интервала дважды может дублировать слова. Для реального улучшения нужны разделение источников либо выравнивание и стратегия атрибуции, а не удаление всех перекрытий.

Из требований кейса: ASR 40, диаризация 25, таймкоды 10, скорость 10, работоспособность/UX 10, защита 5. Пунктуация полезна, но не должна вытеснять диаризацию и проверку APK.

## P2 - устойчивость и скорость

- Измерить пик TOTAL PSS и native heap, RTF и температуру на целевом Android. 4 ГБ - RAM всего устройства, не бюджет процесса.
- Тесты: повторная обработка, отмена, тишина, битый WAV, отказ выбора файла, нехватка диска, 10-минутный предел.
- При превышении памяти сначала уменьшать длину ASR-окна/потоки и выяснять этап роста. Модели уже запускаются последовательно и освобождаются через finally.
- Проверить MP3 и M4A на устройстве: MediaCodec зависит от прошивки.
- Если нужны длинные встречи/сворачивание: foreground service + сохранение промежуточных результатов. Это отдельная работа, не обещание текущего MVP.

## P3 - сдача и полировка

- Положить проверенный APK, SHA-256, измерения и короткое видео в отчётные материалы.
- Записать демонстрацию **чистой** офлайн-установки, импорта и экспорта.
- После этого: воспроизведение по таймкоду, редактирование, улучшение оформления.
- Не добавлять саммари, чат, загрузчик моделей, обучение новой нейросети или миграцию UI до выполнения P0/P1.

## Проверка на Android

```bash
adb install -r android/app/build/outputs/apk/debug/app-debug.apk
# Очистить данные; включить авиарежим вручную до первого запуска
adb shell pm clear ru.neurostenographer
adb shell am start -n ru.neurostenographer/.MainActivity
# Снимать несколько раз во время каждого этапа, не только после завершения
adb shell dumpsys meminfo ru.neurostenographer
adb logcat -d -s NeuroStenographer AndroidRuntime
python3 scripts/evaluate.py exported.json --reference gold.json
```

Записать: модель телефона, Android, ABI, RAM, длительность и формат записи, холодный/тёплый запуск, суммарное время, RTF, максимальный наблюдаемый PSS, факт ошибок/отмены. Время первого запуска включает извлечение весов. Для корректного пика памяти нужен периодический сбор, одиночный `dumpsys` недостаточен. WER-утилита проверяет только текст и схему: это не DER и не метрика атрибуции спикеров.

Для проверки загрузки всех нативных моделей в одном процессе на подключённом Android:

```bash
cd android
./gradlew connectedDebugAndroidTest
```

`NativeSmokeTest` реально запускает диаризацию/ASR на тишине и RUPunct на русском вопросе. Это проверка совместимости JNI и наличия весов, не тест WER/DER и не замена трёх полных записей.
